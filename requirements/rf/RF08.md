# RF08 — Editar os dados cadastrais do aluno

| Campo | Valor |
|---|---|
| **Documentação** | Revisada em 21/10/2026 (DEC-37 a DEC-39) |
| **Implementação** | Planejada |
| **Grupo** | Cadastro |
| **Atualizado em** | 21/10/2026 |

## Objetivo

Manter atualizados os dados do aluno e do contato principal sem perder o histórico de
movimentações nem a evidência do consentimento.

## Descrição

O funcionário edita o cadastro do aluno. Cada mudança segue uma regra:

| O que muda | Como o sistema trata |
|---|---|
| Nome, matrícula, foto | Atualiza o aluno |
| Turma | Encerra o vínculo vigente e cria um novo, para não reclassificar o histórico |
| Telefone e e-mail do contato principal | Atualiza o contato |
| Pessoa do contato principal | Cria um **novo** contato |
| Situação do aluno [DEC-28, D10] | Inativa o aluno |
| Aviso por e-mail ao contato principal | Liga ou desliga `recebe_notificacao`, a pedido do responsável (DEC-38) |

Antes de gravar, o sistema mostra um resumo das alterações para o funcionário confirmar.

## Perfis envolvidos

**FUNCIONARIO** (DEC-37).

## Pré-condições

- O funcionário está autenticado.
- O aluno existe e foi localizado pela busca (RF11) ou pela lista.

## Fluxo principal

1. O funcionário abre **Alunos → [aluno] → Editar**. A página "Editar aluno Ana Teste | Furin
   Access" vem com os dados atuais preenchidos.
2. O funcionário altera um ou mais campos:
   - **Nome:** obrigatório.
   - **Matrícula:** obrigatória e única (RF06).
   - **Turma:** só turmas ativas.
   - **Foto:** obrigatória. Se não enviar uma nova, a atual continua.
   - **Contato principal:** telefone e e-mail, os dois obrigatórios.
3. O funcionário aciona **Revisar alterações**. O sistema mostra um resumo do tipo "antes →
   depois" com as opções **Corrigir** e **Confirmar** (A11 §5.9.12).
4. Ao confirmar, em uma transação, o servidor:
   1. atualiza `aluno.nome` e `aluno.matricula`;
   2. se a turma mudou, preenche `fim_em` = agora no vínculo vigente e cria um novo
      `vinculo_turma` com `inicio_em` = agora;
   3. se a foto mudou, grava o arquivo novo na área privada e atualiza `foto_chave`.
      [DEC-28, D10] Remove o arquivo antigo depois do commit, por minimização;
   4. atualiza `telefone` e `email` do contato principal.
5. O evento `ALUNO_EDITADO` vai para o log com os **nomes** dos campos alterados, sem os
   valores (A10 §8.15).
6. A tela confirma: "Cadastro de Ana Teste atualizado." (`role="status"`).

### Fluxo alternativo A1: trocar a pessoa do contato principal

1. O funcionário aciona **"Substituir contato principal"** e informa nome, telefone e e-mail da
   nova pessoa.
2. O sistema cria um **novo** `contato_responsavel`, com `principal = 1` e
   `recebe_notificacao = 1` (DEC-22).
3. O contato anterior passa a `principal = 0`. O banco garante um único principal ativo
   (coluna gerada UNIQUE).
4. **[DEC-28, D11]** O consentimento já conferido continua válido. Se o grupo exigir um novo
   termo assinado pela nova pessoa, ele é registrado como novo `consentimento` (RF05
   A1).
5. O contato anterior deixa de receber os avisos, porque deixa de ser o contato
   principal ativo [DEC-28, D11].

### Fluxo alternativo A2: inativar o aluno [DEC-28, D10]

1. O funcionário aciona **"Inativar aluno"** e confirma.
2. O sistema confere se há saída pendente. Se houver, a inativação é recusada até a
   saída ser registrada (DEC-04, RN06).
3. O sistema preenche `aluno.ativo = 0`. Novas leituras são recusadas (RN09), e o
   histórico continua disponível (A14 p.5).

### Fluxo alternativo A3: segunda via de carteirinha

Pela mesma página do aluno, conforme o RF07.

### Fluxo alternativo A4: registrar a revogação do termo (DEC-34)

O funcionário registra a revogação conforme o [RF05, fluxo A2](RF05.md). O aluno é inativado e a
carteirinha é revogada. Se houver saída pendente, ela precisa ser registrada antes.

### Fluxo alternativo A5: ligar ou desligar o aviso por e-mail (DEC-38)

1. O responsável pede à escola para não receber (ou voltar a receber) os avisos.
2. Na edição do aluno, o funcionário muda a opção **"Enviar avisos de entrada e saída por
   e-mail ao contato principal"** e confirma.
3. O servidor grava `contato_responsavel.recebe_notificacao` e registra o evento
   `PREFERENCIA_AVISO_ALTERADA` no log, com o autor, o aluno e o novo valor.
4. A mudança vale para as próximas movimentações. As notificações já criadas continuam
   como estão (RF21).

## Exceções e mensagens

| Situação | Mensagem |
|---|---|
| Campo obrigatório vazio | Mesmas mensagens do RF04 |
| Matrícula já usada por outro aluno | Mensagem do RF06 (A11 §5.9.9, §5.9.10) |
| Foto inválida | Orientação conforme os formatos aceitos: **JPEG ou PNG, até 2 MB** (PEND-05, DEC-28) |
| Inativar com saída pendente | "Registre a saída de Ana antes de inativar o cadastro." [PROP] |
| Mudança do aviso por e-mail | Pede confirmação: "Os avisos de Ana Teste deixarão de ser enviados a Carla Teste. Confirmar?" [PROP: texto] |
| Cadastro alterado por outro usuário enquanto este editava | A última gravação prevalece (DEC-28, D10) |

## Dados utilizados

| Dado | Campo | Pode ser editado? |
|---|---|---|
| Nome | `aluno.nome` | Sim |
| Matrícula | `aluno.matricula` | Sim, com unicidade (DEC-28, D10) |
| Foto | `aluno.foto_chave` | Sim (substituição) |
| Turma | `vinculo_turma` | Por novo vínculo, sem editar o vigente |
| Situação | `aluno.ativo` | Sim, pelo fluxo A2 (DEC-28, D10) |
| Telefone e e-mail do contato principal | `contato_responsavel.telefone`, `email` | Sim |
| Nome e pessoa do contato | `contato_responsavel.nome` | Só por um novo contato (A1) |
| Preferência de aviso | `recebe_notificacao` | Sim, a pedido do responsável, com registro no log (DEC-38) |
| Consentimento | `consentimento` | Não é editado. Só se cria um novo (RF05 A1) |

## Regras de negócio relacionadas

- **RN06:** toda entrada exige uma saída (inativação).
- **RN09:** aluno inativo não passa.
- **RN15:** segunda via.
- **RN16:** os dados obrigatórios continuam obrigatórios depois da edição.

## Critérios de aceitação

| ID | Critério |
|---|---|
| CA-RF08-01 | Antes de gravar, o sistema mostra o resumo "antes → depois" com Corrigir e Confirmar. "Corrigir" volta ao formulário com os valores digitados (A11 §5.9.12) |
| CA-RF08-02 | Trocar a turma de 6A para 6B cria um novo vínculo e encerra o anterior. As movimentações antigas **continuam** aparecendo como 6A no histórico |
| CA-RF08-03 | Mudar a matrícula para uma que já existe é recusado (RF06) |
| CA-RF08-04 | Sem enviar uma nova foto, a foto atual continua. Remover a foto sem enviar outra é impossível (DEC-05) |
| CA-RF08-05 | Substituir o contato principal cria um novo registro. O antigo fica `principal = 0`, e só um principal ativo existe |
| CA-RF08-06 | O funcionário desliga o aviso de Bia a pedido do responsável: `recebe_notificacao` vira 0 e o log registra `PREFERENCIA_AVISO_ALTERADA` com o autor. A próxima entrada de Bia não gera notificação (DEC-38) |
| CA-RF08-07 | O log registra `ALUNO_EDITADO` com os nomes dos campos alterados, sem os valores, sem fotos e sem e-mail completo |
| CA-RF08-08 | Inativar um aluno com saída pendente é recusado. Sem pendência, novas leituras passam a ser recusadas e o histórico continua consultável |
| CA-RF08-09 | Sem login, a edição leva à tela de login |
